01

Join & authenticate

Each browser establishes its own session with Neutron.

  1. BROWSER ↻ LOCAL

    Derive the room, keep the PIN

    PBKDF2-SHA-256 (600,000 iterations) derives key material from the PIN. Part produces the room lookup hash; the rest becomes the local encryption root. Both browsers use the same PIN.

  2. BROWSER ⇄ NEUTRON

    Prove access with OPAQUE

    Registration or login exchanges cryptographic proofs, never the PIN. Each browser and the relay establish a session key. Credential records and sessions stay in RAM; the room hash is hashed again for server-side lookup.

02

Encrypt & send

Three content layers, wrapped in a separate transport envelope.

AES-GCM · LAYER 3AES-GCM · LAYER 2AES-GCM · LAYER 1MESSAGE
  1. SENDER ⇄ NEUTRON

    Request a one-time upload key

    A session HMAC authorizes the prepare request. Neutron returns a random message hash, UTC timestamp, and one-time P-256 public key. The sender verifies the HMAC binding that key, hash, and timestamp to its session.

  2. SENDER ↻ LOCAL

    Encrypt three times

    HKDF-SHA-256 derives three distinct AES-256-GCM keys from the PIN-derived root, message hash, and timestamp. The message JSON passes through layers 1 → 2 → 3, each with a fresh nonce. Only the final ciphertext and three nonces are packaged.

  3. SENDER → NEUTRON

    Seal the upload

    The sender generates an ephemeral P-256 key pair. ECDH + HKDF derives a transport key; AES-256-GCM seals the encrypted package. The upload includes the sender’s ephemeral public key and a session HMAC proof bound to the room, message hash, and public key.

  4. NEUTRON ↻ RAM

    Unwrap transport, retain ciphertext

    The relay verifies access and removes only the transport envelope. It stores the outermost content ciphertext, three nonces, message hash, and timestamp in RAM for 15 seconds. It does not receive the PIN, content keys, or message plaintext.

03

Fetch & decrypt

A fresh delivery envelope for each authenticated recipient.

03→02→01
  1. RECIPIENT ⇄ NEUTRON

    Discover every two seconds

    Polling returns active message hashes and timestamps, without content ciphertext. The browser skips hashes it has already displayed or is currently claiming.

  2. RECIPIENT → NEUTRON

    Claim with a fresh public key

    For each unseen message, the recipient generates a new P-256 pair. It submits the public key and a session HMAC proof bound to the room, message hash, and recipient key.

  3. NEUTRON → RECIPIENT

    Wrap for this recipient

    After checking the proof and message expiry, the relay generates a fresh P-256 pair. ECDH + HKDF + AES-256-GCM wraps the stored package for this recipient. A session HMAC authenticates the relay’s public key, message hash, and timestamp.

  4. RECIPIENT ↻ LOCAL

    Verify, unwrap, decrypt

    The browser verifies the relay’s HMAC, opens the transport envelope with its ephemeral private key, then derives the three content keys from the PIN root. It decrypts 3 → 2 → 1 and displays the message with readable UTC time. Ephemeral key pairs are not retained for reuse.

The relay expires its copy after 15 seconds. Messages already displayed remain in the browser until the page is refreshed or closed.
